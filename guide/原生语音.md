# 原生语音条

> © 2026 Raincove ♡ · Roronoa & Haruka · 文档 [CC BY-NC-SA 4.0](../LICENSE) · 代码 [PolyForm Noncommercial 1.0.0](../LICENSE-CODE)
>
> 把一句话说成企业微信的原生语音条：点开即播、长按转文字的那种语音泡泡。本篇只保留企业微信侧的桥接工艺；这门手艺的正典（Telegram 门、网页播放门、场景感语音的工艺配方与台词学问）在独立仓库 **[voice-for-one](https://github.com/RoronoaHaruka/voice-for-one)**（书名《一副声音》）。

## 先看结论

- 两扇门都能发原生语音条：`msgtype=voice`。素材硬边界是 **AMR 格式、不超过 2MB、不超过 60 秒**，三条都是接口侧强制。
- 链路五步：一句话文本 → TTS → MP3/WAV → 8kHz 单声道 PCM → AMR-NB → `media/upload?type=voice` 拿 `media_id`，应用门走 `message/send`，客服门走 `kf/send_msg`。
- TTS 的 key 永远只住在服务器。

```text
一句话文本
   │  TTS（key 只在服务器）
   ▼
MP3/WAV ─ ffmpeg 解码 → 8kHz 单声道 PCM ─ AMR-NB 逐帧编码 ─┐
                                                              ├─ media/upload?type=voice → media_id
      应用门 message/send(msgtype=voice)  ◄───────────────────┤
      客服门 kf/send_msg(msgtype=voice)   ◄───────────────────┘
```

## 格式这一关：AMR-NB

| 约束 | 值 |
|---|---|
| 容器与编码 | AMR（窄带 AMR-NB，8kHz 单声道），文件头 `#!AMR\n` |
| 大小 | ≤ 2MB |
| 时长 | ≤ 60 秒 |
| 素材有效期 | 临时素材三天过期，`media_id` 不可长存 |

多数发行版的 ffmpeg **解**得动 AMR 却**编**不出来（`libopencore_amrnb` 编码器没编译进去）。最稳的两步走：先用 ffmpeg 把任意音频解到 8kHz 单声道 s16le PCM，再调用 `libopencore-amrnb` 的 C 接口逐帧编码，一帧 160 个样本，12.2kbps（mode 7），开头写上 `#!AMR\n`。独立可跑的转换脚本在 voice-for-one 的 [`to_amr.py`](https://github.com/RoronoaHaruka/voice-for-one/blob/main/code/to_amr.py)。系统依赖两件（Debian 系包名）：

```bash
apt install ffmpeg libopencore-amrnb0
```

如果你的 ffmpeg 恰好带编码器，一条命令等价：

```bash
ffmpeg -i voice.mp3 -ar 8000 -ac 1 -c:a libopencore_amrnb voice.amr
```

## 两扇门怎么发

上传与发送是固定两步：`media/upload?type=voice` 换 `media_id`，再按门发送。应用门 `message/send`，`msgtype=voice`；客服门 `kf/send_msg`，同样的 `msgtype`，并且**占用与文本相同的五格回复预算**、使用稳定 `msgid` 接住网络重试，规则与本仓库文本和文件发送一致。自建应用门没有会话条数额度，只有宽裕的接口频控。语音条经微信插件进入个人微信后，显示为原生语音泡泡，可长按转文字。

## 参考实现：voice_sender.py

[`../code/voice_sender.py`](../code/voice_sender.py) 把整条链封成一个受控工具：

```bash
# 顺着队列信封原路回一句语音（应用门或客服门自动选）
python3 code/voice_sender.py --envelope /var/lib/wecom-agent/queue/msg_kf_example.json --text "晚安，今天辛苦了。"
# 主动从应用门说一句
python3 code/voice_sender.py --app-user user_example --text "到家了记得说一声。"
```

防护有五层，每层都有对应的消融项（见 [`ABLATION.md`](../tests/ABLATION.md)）：文本长度上限在 TTS 之前拦截（`WECOM_VOICE_MAX_TEXT_CHARS`，先省下生成费再谈别的）；解码后按 PCM 实际时长校验 `WECOM_VOICE_MAX_SECONDS`；编码后按字节校验 `WECOM_VOICE_MAX_BYTES`（只能调小，不能越过 2MB API 上限）；应用门收件人白名单与客服门绑定客户校验沿用全仓库同一套规则。TTS、解码、编码三步都是可注入的函数，离线测试不碰网络也不需要装编码库。

TTS 选型、台词写法、音色与场景感语音的整套工艺见 [voice-for-one](https://github.com/RoronoaHaruka/voice-for-one)。做 voice clone 只有一条不可让步的规矩：**音源必须是你有权使用的**。

## 一段诚实的边界

这条语音链路属于企业微信自建应用与微信客服两扇官方门。至于各种逆向协议的「个人微信机器人」，其原生语音通道在 2026 年年中之后已被服务端封死：消息显示发送成功，对端永远收不到，且无任何报错。走正门，语音条今天依然到达。

## 电脑微信里是嘟嘟电流？这是桌面客户端的事，不是你的链路

2026.9.6 实测（同一条按本章发出的 AMR-NB 语音）：**手机微信里的企微插件能放，手机企业微信能放，电脑版企业微信能放，只有电脑微信（Mac / Windows，含微信里的企微插件）放不出来**，点开是一串嘟嘟或电流。原因在腾讯那一端：接口上传的语音不会被服务器转码，桌面微信只认微信自家的语音编码，拿到接口上传的 AMR 就解成噪音。

换格式救不了它，别在这上面耗。当晚逐条试过：纯 SILK（微信自家格式）上传被 `301017 voice file only support amr` 打回，上传口只验 `#!AMR` 文件头；给 SILK 套一个 `#!AMR\n` 头能上传能发，但手机、电脑微信、电脑企微三端全哑，客户端按文件头解码；AMR-WB（`#!AMR-WB\n`，16 kHz）能上传能发，同样三端全哑，连原本能放的手机也哑；改从微信客服那扇门（`kf/send_msg`）发同一份 AMR-NB，电脑微信里的客服会话照样不出声，两扇门在腾讯那边是同一套语音存储。把同一条语音当 `msgtype=file` 的 mp3 发过去，电脑微信能用系统播放器放，但那是文件卡片，不是语音条。

一组值钱的对照（群友做的）：拿一条手机录进来的入站语音的 media_id 直接 `message/send`，电脑微信能放；把这同一份文件用 `media/get` 下载、再 `media/upload` 上传，字节和 SHA256 完全一致，新的 media_id 在电脑微信上就变嘟嘟。差别只在客户端拿到接口上传语音之后怎么解。

排查顺序：先 `ffprobe` 本地文件，确认 `codec_name=amr_nb`、`sample_rate=8000`、`channels=1`，再 `ffmpeg -i voice.amr -f null -` 解一遍无报错；然后在**手机企业微信 App** 里点开同一条，能放就说明链路没问题，嘟嘟只是听的那一端。电脑上要听真正的语音条，用电脑版企业微信客户端。手机企微也放不出来时，再回头查 `#!AMR\n` 文件头、每帧 160 个采样、mode 7 这些编码细节，拿本章脚本生成的文件逐字节对照。

## 验证清单

- [ ] 生成的 AMR 以 `#!AMR\n` 开头，8kHz 单声道，60 秒与 2MB 以内。
- [ ] 应用门语音条在**手机**个人微信（微信插件）里显示为可点播的语音泡泡，长按可转文字；电脑微信里放不出来是桌面客户端的事，见上一节。
- [ ] 客服门语音条到达，且五格回复预算相应减一。
- [ ] 超长文本在 TTS 调用**之前**就被拦下。
