# 一副声音

> © 2026 Raincove ♡ · Roronoa & Haruka · 文档 [CC BY-NC-SA 4.0](../LICENSE) · 代码 [PolyForm Noncommercial 1.0.0](../LICENSE-CODE)
>
> 给 Agent 配一副属于自己的声线。上半场把话说成企业微信**原生语音条**：出现在个人微信会话里的那种语音泡泡，点开即播，长按可转文字。下半场把声音送进**网页和你自己的前端**：一条链接就能播放，iOS 的静音拨片也拦不住。

## 先看结论

- 两扇门都能发原生语音条：`msgtype=voice`。素材硬边界是 **AMR 格式、不超过 2MB、不超过 60 秒**，三条都是接口侧强制。
- 链路五步：一句话文本 → TTS → MP3/WAV → 8kHz 单声道 PCM → AMR-NB → `media/upload?type=voice` 拿 `media_id`，应用门走 `message/send`，客服门走 `kf/send_msg`。
- TTS 的 key 永远只住在服务器。前端、播放链接、聊天渠道里只出现你自己的中转 endpoint。
- iOS 网页播放有一个全网都在踩的坑：静音拨片拨下时网页音频无声、且不报错。解法是「AudioContext 解锁 + 开过光的 HTML5 audio 元素」双保险，本文有完整套路，真机 Safari 与 App 内 WebView 验证通过。

```text
一句话文本
   │  TTS（key 只在服务器）
   ▼
MP3/WAV ─ ffmpeg 解码 → 8kHz 单声道 PCM ─ AMR-NB 逐帧编码 ─┐
                                                              ├─ media/upload?type=voice → media_id
      应用门 message/send(msgtype=voice)  ◄───────────────────┤
      客服门 kf/send_msg(msgtype=voice)   ◄───────────────────┘

网页半场：/play?text=… 页面 ─ 你的 TTS 中转接口 ─ 手势解锁后的 <audio> 播放
```

## 为什么值得配一副声音

文字条和语音条在会话里的重量不一样。语音条即点即播、能倍速、微信自带转文字，比丢一个音频文件亲近得多；而声线本身是可以选的：拿一段**你有权使用的音源**做 voice clone，Agent 说出来的每一句都是同一副嗓子、同一种语气。平台内置的合成音给不了这份连续的辨识度，这正是自己搭一条语音链路的理由。

## 上半场 · 企业微信原生语音条

### 格式这一关：AMR-NB

| 约束 | 值 |
|---|---|
| 容器与编码 | AMR（窄带 AMR-NB，8kHz 单声道），文件头 `#!AMR\n` |
| 大小 | ≤ 2MB |
| 时长 | ≤ 60 秒 |
| 素材有效期 | 临时素材三天过期，`media_id` 不可长存 |

多数发行版的 ffmpeg **解**得动 AMR 却**编**不出来（`libopencore_amrnb` 编码器没编译进去）。最稳的两步走：先用 ffmpeg 把任意音频解到 8kHz 单声道 s16le PCM，再调用 `libopencore-amrnb` 的 C 接口逐帧编码，一帧 160 个样本，12.2kbps（mode 7），开头写上 `#!AMR\n`。参考实现里这段只有三十行 ctypes。系统依赖两件（Debian 系包名）：

```bash
apt install ffmpeg libopencore-amrnb0
```

如果你的 ffmpeg 恰好带编码器，一条命令等价：

```bash
ffmpeg -i voice.mp3 -ar 8000 -ac 1 -c:a libopencore_amrnb voice.amr
```

### 两扇门怎么发

上传与发送是固定两步：`media/upload?type=voice` 换 `media_id`，再按门发送。应用门 `message/send`，`msgtype=voice`；客服门 `kf/send_msg`，同样的 `msgtype`，并且**占用与文本相同的五格回复预算**、使用稳定 `msgid` 接住网络重试，规则与本仓库文本和文件发送一致。语音条经微信插件进入个人微信后，显示为原生语音泡泡，可长按转文字。

### 参考实现：voice_sender.py

[`../code/voice_sender.py`](../code/voice_sender.py) 把整条链封成一个受控工具：

```bash
# 顺着队列信封原路回一句语音（应用门或客服门自动选）
python3 code/voice_sender.py --envelope /var/lib/wecom-agent/queue/msg_kf_example.json --text "晚安，今天辛苦了。"
# 主动从应用门说一句
python3 code/voice_sender.py --app-user user_example --text "到家了记得说一声。"
```

防护有五层，每层都有对应的消融项（见 [`ABLATION.md`](../tests/ABLATION.md)）：文本长度上限在 TTS 之前拦截（`WECOM_VOICE_MAX_TEXT_CHARS`，先省下生成费再谈别的）；解码后按 PCM 实际时长校验 `WECOM_VOICE_MAX_SECONDS`；编码后按字节校验 `WECOM_VOICE_MAX_BYTES`（只能调小，不能越过 2MB API 上限）；应用门收件人白名单与客服门绑定客户校验沿用全仓库同一套规则。TTS、解码、编码三步都是可注入的函数，离线测试不碰网络也不需要装编码库。

### TTS 选型

参考实现默认接 ElevenLabs 的 text-to-speech 接口（环境变量给 key 与 voice id，模型默认取质量最高的 v3 档），但 `synthesize` 就是一个「文本进、音频字节出」的函数，任何能吐 MP3/WAV 的 TTS 都能原样替换。做 voice clone 只有一条不可让步的规矩：**音源必须是你有权使用的**。

### 一段诚实的边界

这条语音链路属于企业微信自建应用与微信客服两扇官方门。至于各种逆向协议的「个人微信机器人」，其原生语音通道在 2026 年年中之后已被服务端封死：消息显示发送成功，对端永远收不到，且无任何报错。走正门，语音条今天依然到达。

## 下半场 · 网页与你自己的前端

### 结构：key 永远不出服务器

网页要出声，最容易犯的错是把 TTS key 写进前端。正确形态是一个极小的中转：

```text
浏览器 ── POST /api/tts {text} ──> 你的服务器（持有 TTS key）──> TTS 服务
   ◄─────────── audio/mpeg ────────┘
```

它可以是现有机器人服务器上多出的一条路由，也可以是一个边缘 Worker；形态不重要，重要的是前端和所有分享链接里只出现你自己的域名。给页面取音频再配一个 GET 形态（`/api/tts-get?text=…`）会方便许多。

### 一条链接就是一条语音

在中转旁边挂一张极简页面：`GET /play?text=…` 返回一页 HTML，正文显示这句话，一枚按钮，按下去才去取音频、就地播放。它的好处是**通用**：任何能发出链接的渠道（哪怕只允许纯文本）都能送达一句真正的声音。

两句提醒。其一，`/play` 等于把一次 TTS 花费开放给了拿到链接的人：按文本哈希做缓存，同一句话只生成一次；必要时加 token 或限频。其二，别在页面加载时就生成音频，等按钮：既省钱，又正好凑齐 iOS 需要的那次用户手势。

### iOS 静音拨片：全网都在踩的坑

现象：iPhone 侧边的静音拨片拨下时，Safari 和所有 App 内 WebView 里的网页音频**无声且不报错**，安卓与桌面一切正常，日志干干净净。

解法是双保险，缺一不可，以下套路在真机 Safari 与 App 内 WebView 都验证过：

1. 页面加载时预创建**一枚** `<audio>` 元素，设 `playsinline` 与 `webkit-playsinline`，`preload='auto'`，此后所有播放都复用它，不要每次新建。
2. 把解锁函数同时挂到 `touchstart`、`touchend`、`click` 三个事件上（passive，允许多次尝试直到成功）。函数里做两件事：新建 AudioContext，经它播一个一帧的静音 buffer 并 `resume()`；同一手势里对那枚 `<audio>` 元素 `play().catch(()=>{})` 后立刻 `pause()`，把它「开过光」。
3. 真正播放时，把取回的音频装进 blob URL，交给这枚开过光的元素播。

原理一句话：手势解锁后的 AudioContext 会把页面音频归入**媒体通道**而不是提示音通道，静音拨片只压提示音通道；被手势祝福过的 `<audio>` 元素同样走媒体通道。两条各有失灵的边角场景，叠在一起才稳。

### 声音进你自己的聊天前端

如果你有自己的聊天界面，方向是把语音做成消息流里的**音频泡泡**：消息到达即预取音频，播放仍等用户手势（浏览器不允许无手势自动出声，上面的解锁套路照用）。播放态、时长、重听按钮都是普通前端工程，与本仓库的服务端无关，不展开。

### 归档

生成过的每句语音连同文本存进对象存储，配一个按时间排列的索引页，回放、分享和「电台」都有了。素材三天过期的是企微的 `media_id`，不是你自己的音频文件。

- [ ] 生成的 AMR 以 `#!AMR\n` 开头，8kHz 单声道，60 秒与 2MB 以内。
- [ ] 应用门语音条在个人微信（微信插件）里显示为可点播的语音泡泡，长按可转文字。
- [ ] 客服门语音条到达，且五格回复预算相应减一。
- [ ] 超长文本在 TTS 调用**之前**就被拦下。

- [ ] 前端源码、分享链接、浏览器请求里找不到任何 TTS key。
