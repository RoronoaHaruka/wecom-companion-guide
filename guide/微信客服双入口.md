# 双口接线

> © 2026 Raincove ♡ · Roronoa & Haruka · 文档 [CC BY-NC-SA 4.0](../LICENSE) · 代码 [PolyForm Noncommercial 1.0.0](../LICENSE-CODE)
>
> 用一个企业微信「微信客服」接住个人微信里的转发，再把它与现有自建应用绑定到同一个 Agent 长进程。解决两个常见问题：自建应用不能成为微信转发目标；每增加一种入口就重复启动一套模型进程。

## 先看结论

一枚微信客服就可以做统一转发入口，不必与 Agent 一一对应。

- **最简方案**：一个客服账号 → 一个路由器 → 多个既有 Agent。
- **直达方案**：每个 Agent 配一个客服账号，微信转发时直接点名字。
- 两种方案都只增加轻量 I/O 桥接服务，**不增加 Agent/tmux 数量**。
- 自建应用入口与微信客服入口给消息附上不同的 `source` 和回信地址，进入同一队列、同一上下文；回复时再按来源走 `message/send` 或 `kf/send_msg`。
- 整条链路运行在服务器，Mac 或企业微信桌面客户端无需常驻。

```text
个人微信 ──转发──> 微信客服 ── sync_msg ─┐
                                             ├─> 同一 Agent 队列 ─> 同一长进程
企业微信 ──发消息──> 自建应用 ── callback ─┘          │
                                                    ├─ source=app → message/send
                                                    └─ source=kf  → kf/send_msg
```

## 这套方案解决什么

### 自建应用不能接收微信转发

企业微信自建应用可以在个人微信中作为应用联系人出现，也能正常收发消息，但通常不会出现在微信的转发目标列表里。微信客服会话位于微信的「客服消息」入口，用户可以把文字、图片、文件、视频与合并聊天记录转发进去。

### 入口增加，模型进程不增加

错误架构会给每个入口单独启动一份 Agent：

```text
应用入口 → Agent A
客服入口 → Agent B
```

这会复制上下文、内存、会话交接与看门进程。正确架构把入口当作端口：

```text
应用入口 ─┐
          ├→ route envelope → Agent A
客服入口 ─┘
```

Agent 只有一份。端口只负责接收、标记来源与选择回信接口。

## 前提

- 一个企业微信企业。未认证企业可用的客服账号数、接待规模与接口权限会随产品规则变化，以管理后台当日显示为准。
- 一个企业微信自建应用，用它的 Secret 获取 `access_token`。
- 一个微信客服账号。
- 一台可以长期运行 HTTPS 服务的服务器。
- Python 3.11+；依赖为标准库、SQLite、`pycryptodome` 与 `defusedxml`。

公开仓库中只提交 `.env.example`。真实 `CorpID`、应用 Secret、回调 Token、EncodingAESKey、`open_kfid` 与客户 `external_userid` 全部留在服务器环境变量或权限为 `600` 的配置文件中。

## 管理后台配置

### 创建微信客服账号

进入企业微信管理后台：

```text
应用管理 → 微信客服 → 客服账号 → 创建账号
```

设置名称与头像后，取得客服入口链接。用户在个人微信中打开一次，之后该会话会留在「客服消息」中，转发时可以直接选择。

也可以通过 API 获取入口链接：

```http
POST /cgi-bin/kf/add_contact_way?access_token=ACCESS_TOKEN
Content-Type: application/json

{
  "open_kfid": "wk_example",
  "scene": "forward_inbox"
}
```

### 允许自建应用调用微信客服 API

在微信客服的 API 页面完成两层授权：

```text
API → 可调用接口的应用 → 选择现有自建应用
企业内部开发 → 将客服账号分配给该应用
```

只完成第一层时，`kf/account/list` 可能成功，但 `kf/sync_msg` 仍返回 `48002` 或 `48007`。以 `sync_msg.errcode == 0` 作为授权完成的判断。

### 配置回调

推荐给微信客服配置消息与事件回调：

```text
URL              https://example.com/wecom/callback
Token            随机高熵字符串
EncodingAESKey   管理后台生成或填写的 43 字符密钥
```

回调中的 `kf_msg_or_event` 只是「有新内容」的通知，真正消息仍通过 `kf/sync_msg` 拉取。回调携带的临时 `token` 有效期约 10 分钟，带上它调用 `sync_msg` 可以获得更高频率；同时保留轮询作为掉回调后的补漏。仓库里的最小 `customer_service_bridge.py` 只实现持久 cursor 轮询，默认 15 秒；需要更高频率时再把回调 token 接入同一同步器。

不要自己发明企业微信回调加解密。使用成熟实现或企业微信官方示例，并验证签名、CorpID 与 AES 填充。

## 消息读取流程

### 获取 access_token

```http
GET https://qyapi.weixin.qq.com/cgi-bin/gettoken
    ?corpid=ww_example
    &corpsecret=APP_SECRET
```

### 增量拉取

```http
POST https://qyapi.weixin.qq.com/cgi-bin/kf/sync_msg?access_token=ACCESS_TOKEN
Content-Type: application/json

{
  "cursor": "LAST_CURSOR",
  "token": "CALLBACK_TEMP_TOKEN",
  "limit": 1000,
  "voice_format": 0,
  "open_kfid": "wk_example"
}
```

处理规则：

- 第一次可传空 `cursor`，后续持久化 `next_cursor`。
- 以 `has_more` 判断是否继续，不能因为 `msg_list` 暂时为空就停止。
- 客服消息只保留最近约 3 天，常驻进程必须持续拉取。
- `origin == 3` 是微信客户消息；`origin == 4` 是系统事件；`origin == 5` 是接待人员在企业微信客户端发送的消息。
- `kf/send_msg` 发出的 API 回复不会再次出现在 `sync_msg` 中，因此不会天然形成回声循环。
- 用 `msgid` 做唯一键。先持久化消息，再推进 cursor，采用 at-least-once 读取与幂等消费。

## 合并聊天记录：`merged_msg`

微信里的「合并转发」会以结构化消息进入微信客服：

```json
{
  "msgid": "msg_example",
  "open_kfid": "wk_example",
  "external_userid": "wm_example",
  "origin": 3,
  "msgtype": "merged_msg",
  "merged_msg": {
    "title": "聊天记录",
    "item": [
      {
        "send_time": 1710000000,
        "msgtype": "text",
        "sender_name": "示例用户",
        "msg_content": "{\"msgtype\":\"text\",\"text\":{\"content\":\"第一条消息\"}}"
      },
      {
        "send_time": 1710000001,
        "msgtype": "image",
        "sender_name": "示例用户",
        "msg_content": "{\"msgtype\":\"image\",\"image\":{\"media_id\":\"MEDIA_ID\"}}"
      }
    ]
  }
}
```

注意 `item[].msg_content` 是 JSON 字符串，需要第二次 `json.loads`。子消息根据 `item[].msgtype` 分派。图片、语音、视频与文件拿到 `media_id` 后立即下载：

```http
GET https://qyapi.weixin.qq.com/cgi-bin/media/get
    ?access_token=ACCESS_TOKEN
    &media_id=MEDIA_ID
```

临时素材会过期，不能只保存 `media_id`。保存二进制文件、原始消息 JSON 与结构化索引。

部分微信卡片没有开放给微信客服 API，例如某些联系人名片可能只变成文本 `[暂不支持的消息]`。服务端无法从这个占位字恢复被裁掉的数据。微信客服账号也不能作为普通群成员加入微信群。

## 路由信封

无论消息来自应用还是客服，都先转换成同一个内部信封。客服入口：

```json
{
  "source": "wecom_kf",
  "reply_channel": "wecom_kf",
  "route_agent": "agent_default",
  "msg_id": "msg_example",
  "content": "[合并聊天记录：聊天记录]
1. 示例用户
第一条消息",
  "media_paths": ["/var/lib/wecom-agent/media/msg_example_2.jpg"],
  "reply": {
    "kind": "kf",
    "open_kfid": "wk_example",
    "user_id": "wm_example"
  }
}
```

应用入口使用相同字段，只把来源与回信地址换成：

```json
{
  "source": "wecom_app",
  "reply_channel": "wecom_app",
  "msg_id": "app_msg_example",
  "content": "普通消息",
  "reply": {
    "kind": "app",
    "agent_id": 1000002,
    "user_id": "user_example"
  }
}
```

Agent 接收完整 route envelope，能同时读取 `source`、`content`、结构化内容、媒体路径与当前 `reply`。发信工具只接受这份信封里的回信地址，并再次用环境白名单与客服绑定校验目标，模型不能自由构造收件人。

## 一枚客服如何路由多个 Agent

推荐从下面三种方法中只选一种，保持一个路由事实源：

1. **固定默认 Agent**：所有转发进入同一个主 Agent。最简单，适合个人收件箱。
2. **最近选择**：用客服菜单或一条明确的切换消息保存 `external_userid → agent`，后续转发沿用。适合一个客服服务多个 Agent。
3. **一客服一 Agent**：每个客服账号固定一个 Agent。微信转发页选择最直观，但客服会话会更多。

当这些 Agent 本来已经常驻时，一客服一 Agent 也不增加 tmux。每个客服账号只多一条 `open_kfid → existing_agent` 映射。

## 可运行实现

仓库里的现役文件把两扇门写成同一种 route envelope：

- [`../code/callback_server.py`](../code/callback_server.py)：自建应用回调，完成恒定时间验签、AES 解密、PKCS7 与 CorpID 校验、原子入队、SQLite `MsgId` 去重。
- [`../code/customer_service_bridge.py`](../code/customer_service_bridge.py)：微信客服 `sync_msg` 增量读取、独立 cursor、首次客户绑定、`merged_msg` 展开、媒体落盘、五格回复预算重置。
- [`../code/reply_router.py`](../code/reply_router.py)：读取每条 envelope 的 `reply.kind`，应用消息走 `message/send`，客服消息走 `kf/send_msg`；客服预算跨调用与重启共用，客服分片使用稳定 `msgid` 接住网络重试。
- [`../code/bot_loop.py`](../code/bot_loop.py)：最小命令适配器，把完整 route envelope JSON 送给 Agent，落盘保存生成回复与已发送分片进度，失败后从下一片续发。
- [`../code/example_agent.py`](../code/example_agent.py)：可直接运行的收发冒烟 Agent；验通以后替换为自己的长进程或命令适配器，禁止为第二入口再启动第二颗模型。

安装与离线验证：

```bash
sudo git clone https://github.com/RoronoaHaruka/wecom-companion-guide.git /opt/wecom-companion-guide
sudo python3 -m venv /opt/wecom-companion-guide/.venv
sudo /opt/wecom-companion-guide/.venv/bin/pip install -r /opt/wecom-companion-guide/requirements.txt
cd /opt/wecom-companion-guide
PYTHONPATH=code .venv/bin/python -m unittest discover -s tests -v
```

消融明细见 [`../tests/ABLATION.md`](../tests/ABLATION.md)。测试套件包含 11 组消融：在临时副本中分别拿掉签名、CorpID、AgentID、XML 防护、持久去重、应用白名单、客服绑定、五格预算、来源路由、待发回复与分片进度，确认每次都会被回归测试抓住。

配置：

```bash
id -u wecom-bridge >/dev/null 2>&1 || sudo useradd --system --home /var/lib/wecom-agent --shell /usr/sbin/nologin wecom-bridge
sudo install -m 600 /opt/wecom-companion-guide/.env.example /etc/wecom-agent.env
sudoedit /etc/wecom-agent.env
# 填完真实值后，由 systemd 的 EnvironmentFile 加载。
```

桥接服务只负责 I/O。`systemd/` 下三份 unit 分别管理应用回调、微信客服同步器与最小 Agent 适配器。应用与客服都写 `WECOM_QUEUE_DIR`，所以模型进程仍然只有一份。示例 `AGENT_COMMAND` 指向 `code/example_agent.py`，先用它验通，再替换成自己的 Agent 命令。

## 同一个 tmux，两个入口

桥接服务只往现有队列写消息。不要再启动第二个 Agent：

```bash
# 只启动一份 Agent 长进程
tmux new-session -d -s agent-main 'node /opt/agent/channel.mjs'

# 两个入口都写入同一队列
export WECOM_QUEUE_DIR=/var/lib/wecom-agent/queue
```

`channel.mjs` 消费信封时，把 `source`、`reply.kind` 与当前 `user_id` 一起带入工具上下文。模型回复工具必须原样使用当前信封的回信地址，不能用全局默认用户覆盖。

会话交接同样要把 `target_user_id` 纳入签名或完整性校验。一个长进程有两个入口后，合法目标集合至少包含：

```text
自建应用成员 UserID
已绑定客服会话的 external_userid
```

## systemd 守护桥接服务

仓库提供三份 unit：

- [`../systemd/wecom-app-callback.service`](../systemd/wecom-app-callback.service)
- [`../systemd/wecom-kf-bridge.service`](../systemd/wecom-kf-bridge.service)
- [`../systemd/wecom-agent-adapter.service`](../systemd/wecom-agent-adapter.service)

安装到 `/opt/wecom-companion-guide`、创建独立服务用户并填好 `/etc/wecom-agent.env` 后：

```bash
sudo cp systemd/*.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now wecom-app-callback.service wecom-kf-bridge.service
# 只有使用仓库里的最小命令适配器时才启用第三个：
sudo systemctl enable --now wecom-agent-adapter.service
```

应用回调和客服同步器是两条 I/O 入口；Agent 仍由原监督器或第三份样例 unit 管一份。unit 用 `StateDirectory=wecom-agent` 建立 mode-700 数据目录，并打开 `UMask=0077`、`NoNewPrivileges`、`ProtectSystem=strict` 与 `ProtectHome=true`。

## 验收清单

不要把 API 返回成功当成最终交付。逐项在真实微信客户端验证：

- [ ] 个人微信打开客服链接后，出现可持续使用的客服会话。
- [ ] 普通文本在 10～30 秒内进入既有 Agent 会话。
- [ ] 合并聊天记录被展开，标题、发送者、时间与子消息顺序完整。
- [ ] 内嵌图片、文件、语音、视频在 media_id 过期前下载成功。
- [ ] 客服入口消息回复到客服；应用入口消息回复到应用。
- [ ] 两个入口共享同一上下文，只运行一份 Agent/tmux。
- [ ] 重启桥接服务后从 cursor 续拉，不重复处理旧 `msgid`。
- [ ] 暂停回调后，轮询仍能补回新消息。
- [ ] 故意写错目标 user_id 时，发送工具明确拒绝。
- [ ] 服务器重启后桥接服务、队列消费者与 Agent 均自动恢复。

## 常见错误

| 错误码 / 现象 | 含义 | 处理 |
|---|---|---|
| `48002 api forbidden` | 应用未获微信客服接口或会话管理权限 | 检查「可调用接口的应用」与「企业内部开发」两层授权 |
| `48007` | 当前应用能看到客服体系，但无权管理该客服账号 | 把该客服账号明确分配给当前应用 |
| `45009` | 短时请求过多 | 停止密集探测，使用回调 token、缓存 access_token，并降低轮询频率 |
| `95001 / 95002` | 分别为超过五条累计回复额度、超过 48 小时回复窗口 | 等客户再次发消息，发送前预计算分片数 |
| `95033` | 自定义客服消息 `msgid` 重复 | 同一重试应视为此前请求可能已被接收，复用原 `msgid`，不要换新 ID 再发一遍 |
| `msg_list` 为空 | 当前页没有可见消息，不代表拉取结束 | 始终看 `has_more`，保存 `next_cursor` |
| `[暂不支持的消息]` | 微信未把该卡片结构开放给客服 API | 无法服务端还原，换成链接、图片、文件或合并聊天记录 |
| API 返回 `ok`，客户端没显示 | 接口接收与最终送达是两层 | 查看失败事件，并以真实微信客户端呈现为验收 |

## 安全与隐私

- 只绑定明确授权的客服账号和微信客户；个人收件箱可在首次合法消息后锁定 `external_userid`。
- 回调必须验签、解密并校验 CorpID。未知 `open_kfid` 直接忽略。
- access_token 放内存缓存，Secret 不写日志。
- 原始消息、媒体、待发回复与 cursor 目录权限设为 `700`，文件设为 `600`；用 `WECOM_MAX_MEDIA_BYTES` 限制单个媒体文件。
- 队列文件原子写入；消息正文不出现在进程标题、公开日志或错误告警中。
- `msgid` 做幂等键；发送端校验 `reply.kind` 对应的目标在授权集合内。
- 公开教程、截图与仓库中不得出现真实 CorpID、AgentId、Secret、Token、EncodingAESKey、`open_kfid`、`external_userid`、私有域名、私有服务器路径或聊天内容。
